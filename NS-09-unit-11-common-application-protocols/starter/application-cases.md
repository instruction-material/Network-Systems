# Constructed application-protocol cases

These fictional records are supplied for reasoning. They were not generated by
the loopback program and do not describe an external site.

## A: a negative DNS answer and a transport failure

An explicit DNS query to an authorized local resolver for missing.example.invalid
returns NXDOMAIN. Another query to a different selected resolver receives no
reply before its deadline. Neither record includes an application connection.
Identify which result is a DNS message and which has no received DNS response.
State what additional authorized observation is needed before blaming an HTTP
listener. Reuse the earlier DNS/NSS lab's distinction between explicit DNS and
system name-service lookup; do not treat this fictional table as a new lookup.

## B: TLS identity and an HTTP decision

One HTTPS client reports an untrusted certificate issuer before receiving any
HTTP status. A second, separately scoped test establishes a trusted TLS identity
for its intended host and receives HTTP 401. Explain why the two records do not
locate the same boundary. A 401 alone does not prove application account access.
Do not disable certificate checks as a substitute for identifying the intended
peer, applicable trust configuration and authorized authentication method.

## C: SSH server identity and account authentication

A client connects but reports a changed server host key. A separate connection
whose expected host key is independently verified reaches an account prompt and
ends with public-key authentication denied. Separate transport, host identity
and account authorization. Identify the trusted evidence needed before changing
a remembered host key. Neither record establishes a successful remote command.

For each case, preserve the stated issuing context, earliest unsupported
boundary, two possible explanations when appropriate, next authorized check and
what that check would fail to prove. No remediation is performed by this file.
